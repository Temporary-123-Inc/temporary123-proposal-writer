# Temporary 123 Proposal Writer

When the user submits a solicitation or project link in the established Proposal Writer workflow, read it and produce a complete editable Word proposal for that opportunity, including a personalized cover letter. The link itself is sufficient instruction to start; the user does not need to repeat the Word, cover-letter, price-book, or image-source preferences. Use Temporary 123, Inc. as the proposer unless the user names another company. Match the previously reviewed proposal's formal, practical writing style and section flow.

## Read the submitted link

Open each supplied opportunity/project link using the relevant connected tool when available, or web browsing for public pages. Read the notice and available solicitation, SOW/PWS, pricing schedule, amendments, Q&A, and attachments needed to draft the response. A summary or search snippet alone is insufficient when the underlying documents are available. Apply later amendments to the requirements they change. Compare full deadline timestamps, including the agency time zone, before declaring an opportunity closed. Follow the buyer's required response format, page limits, submission instructions, and evaluation criteria.

For Google Docs or Drive links, use available authorized Docs/Drive tools and host guidance to read the supplied content. Read the matching host skill when available; otherwise use the authorized connector/browser capabilities without assuming Codex plugin skills exist. If a link needs an existing browser login, use the available browser access when appropriate; never invent unavailable attachment contents. If access is incomplete, explain exactly what could not be read, ask for the missing material needed for this response and continue supported sections while waiting. If no substantive project information is accessible, ask for the opportunity text or attachment rather than fabricating a project.

Read [references/proposal-blueprint.md](references/proposal-blueprint.md) for the drafting structure. `assets/reference-export.pdf` and `assets/reference.png` retain the old proposal as a writing/style reference; consult them only when useful. Do not require access to the old Google Doc, copy it, or recreate its cover artwork before drafting. It is not evidence that its company claims, prices, or commitments apply to the new project.

### Ask for missing information before finalizing

After checking the existing records, ask the user early for any information this proposal needs that is missing, contradictory or unsupported. If Drive search returns no useful result, directly browse the designated folder and relevant child folders before calling an item unavailable. If access fails, identify that limitation and ask for the affected required facts or file. Ask only the actual unanswered questions for this opportunity, in a concise consolidated set, and explain what each answer will complete. Do not turn one solicitation's staffing, forms or other requirements into a standard questionnaire for every proposal.

Continue independent drafting while answers are pending. Wait for the user's answer on dependent content; silence is not an answer. Do not deliver a proposal with unanswered required factual or pricing fields unless the user explicitly requests an incomplete draft. In that case identify each unresolved item and the document's incomplete status. Normal unsigned signature and execution-date lines are allowed. Distinguish facts needed for the bid from details legitimately coordinated after award; describe supported future processes without inventing their outcomes.

Keep each unresolved item once in an internal completion list outside the buyer-facing proposal. Instructions such as "Attach", "Complete", "Confirm" and "Recheck" belong there. Do not remove a required answer, substitute a guess or claim compliance to hide a gap.

Do not present unconfirmed SAM/GSA status, UEI/CAGE/NAICS identifiers, certifications, HUD/ADA compliance, equipment features, response times, staff eligibility, insurance or past performance as established facts. A buyer requirement is not proof of the proposer's capability. Clearly distinguish a supported proposed arrangement from a confirmed commitment, and ask about required unsupported claims. Draft certification language for review only when required; leave execution dates and signatures blank until provided. Reuse an applicable existing executed form after checking its details and validity; never manufacture a signature.

## Draft the proposal

Follow the blueprint and produce full narrative sections, not just headings or a questionnaire. In the absence of buyer-mandated order, use:

- Project/title information, personalized cover letter, and table of contents with verified pagination.
- **1. Company Overview**, including Core Company Information.
- **2. Technical Approach**, using the four delivery phases plus safety, utilities, and readiness.
- **3. Equipment Specifications**.
- **4. Price Proposal**.
- **5. Past Performance**.
- **6. Required Documentation**, with solicitation-specific subsections.

Use consecutive numbering; the example accidentally skips section 3. Do not add a separate executive summary or schedule by default: the cover letter provides the opening overview and the technical phases explain delivery. Add or reorganize sections when the actual solicitation or user requires it.

Write in the proposer's voice, with clear paragraphs explaining the solution, execution, and operational benefit. Use bullets for concrete provisions and tables for pricing and reference records. Match the sample's level of practical detail without padding, repetitive promises, or unsupported superlatives. Adapt the title information, letter, narrative sections, equipment details, prices, and documentation to the new opportunity. Use actual requirements and evaluation factors to make the draft specific, rather than replacing names in generic prose.

Use the normalized catalog and price book to populate matching supported rates rather than leaving all prices TBD. Before questions, show the known products, quantities, billing periods, rates, supported extensions and actual missing components. A price-book product family may be recommended even when the physical inventory lacks its ItemID; do not invent make/model fields or make optional model detail a bid blocker. Match the exact equipment type, size/configuration, billing period and qualifying rental term. Show quantity, unit/billing basis, rate and extension, and retain the source page and calculation in working notes. Calculate rental, delivery, servicing and other supported charges according to the book and the buyer's schedule. For standalone service charges, use per-visit pricing and recommend two visits per month when the contract is silent, under the user's standing pricing rule. Explicit contract frequency takes precedence; retain explicit staffing/day, supplies/week, accessory/month and transport units. Do not invent a daily rental rate, multi-year discount, missing service dollar amount, escalation, tax treatment or all-inclusive price. If a component or billing basis is missing, ask about that component and affected totals while retaining supported calculations. Keep pricing assumptions or commercial gaps outside an eventual submitted bid when the solicitation prohibits qualifications or alternate terms.

For rentals with no stated duration, apply the user's standing flat monthly minimum: the published amount covers one continuous rental of one day, one week or up to one month at the same price. This excludes standalone services and one-time charges and preserves explicitly stated rental periods. Do not prorate or multiply this amount by consecutive days/weeks; use actual billed months for longer rentals. The source's unstated duration is resolved by this user policy and does not require another question. For detailed billing rules, per-visit/monthly conversions, user-approved overrides or equipment substitutions, read [references/pricing-decisions.md](references/pricing-decisions.md). Every two weeks is not twice monthly. Apply the standing service default without asking for approval again, showing per-visit rate x proposed/required visits when a monthly price is needed. Ask only about an unresolved conversion or missing dollar amount; do not turn a 14-day contract cycle into twice-monthly service. Keep past project approvals scoped to that project. Describe a nonmatching offered model accurately and flag required buyer clarification; a larger unit or approved price does not prove technical compliance.

When the requested equipment has no exact supported product match, or the need calls for multiple units/product types, follow [references/product-selection.md](references/product-selection.md) during workflow step 3. Show suitable listed options or combinations, product quantities, fit/differences and sourced proposed values with their billing basis and missing costs. Recommend a defensible option and ask the proposal writer/user to select before finalizing dependent equipment/pricing; reuse an existing choice or explicit selection delegation. Keep unsupported stock/specifications and any buyer-acceptance issue explicit. An exact supported single-product match does not require an extra selection question.

Check identity and contact consistency; scope, equipment counts and capacity; dates/duration and service frequency; utility/access responsibilities; pricing math and billing units; source support for claims; required clauses and attachments; sequential headings and matching contents. Ensure references describe real approved projects. Replace old project details in the current opportunity's title, cover letter, scope, pricing and contact fields; preserve historical facts and reference contacts intentionally cited in Past Performance. Do not sign or claim completion of a certification on the user's behalf.

Keep source links, price-book page references/calculations, and a concise source/access note outside the client-facing proposal, so the user can trace material requirements and rates. Never claim an attachment is enclosed when it has not been supplied or actually included. For the default Word deliverable, follow the [shared Word workflow](references/word-workflow.md) and the matching host adapter's structural/visual checks, using the Documents skill when available. Update contents/page references after layout is stable. Confirm the file contains the cover letter, complete proposal, pricing tables and selected images before returning it.

Before delivery, review every unresolved field and internal completion instruction. Verify that existing pricing and past-performance sources were used and that every genuinely missing required item was asked about and answered, or the user explicitly requested an incomplete draft. Preserve normal unsigned execution lines, listing required execution as unfinished for submission readiness. Follow [references/delivery-report.md](references/delivery-report.md) to report the actual saved Word link/public-view status, all placeholders and unfinished actions with final rendered pages and needed content, an evidence-based readiness percentage, and contract-specific winning prospects/improvements. Never guess pages, public access or competitive odds. Include the source-status table within **Readiness**, outside the client Word file. Creation does not authorize signing, outreach or bid submission; generated-output public viewing is explicitly authorized by the user.
