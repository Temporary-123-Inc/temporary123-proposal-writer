# Temporary 123 Proposal Writer

When the user submits a solicitation or project link in the established Proposal Writer workflow, read it and produce a complete editable Word proposal for that opportunity, including a personalized cover letter. The link itself is sufficient instruction to start; the user does not need to repeat the Word, cover-letter, price-book, or image-source preferences. Use Temporary 123, Inc. as the proposer unless the user names another company. Match the previously reviewed proposal's formal, practical writing style and section flow.

## Read the submitted link

Open each supplied opportunity/project link using the relevant connected tool when available, or web browsing for public pages. Read the notice and available solicitation, SOW/PWS, pricing schedule, amendments, Q&A, and attachments needed to draft the response. A summary or search snippet alone is insufficient when the underlying documents are available. Apply later amendments to the requirements they change. Follow the buyer's required response format, page limits, submission instructions, and evaluation criteria.

For Google Docs or Drive links, use the matching Google Drive/Docs tools and skill to read the supplied content. If a link needs an existing browser login, use the available browser access when appropriate; never invent unavailable attachment contents. If access is incomplete, explain exactly what could not be read. Draft the supported sections with specific placeholders for the missing requirements. If no substantive project information is accessible, ask for the opportunity text or attachment rather than fabricating a project.

Read [references/proposal-blueprint.md](references/proposal-blueprint.md) for the drafting structure. `assets/reference-export.pdf` and `assets/reference.png` retain the old proposal as a writing/style reference; consult them only when useful. Do not require access to the old Google Doc, copy it, or recreate its cover artwork before drafting. It is not evidence that its company claims, prices, or commitments apply to the new project.

## Default deliverable

Do not take over the user's desktop or automate native applications while writing proposals. Use file tools, connected Google Docs/Drive tools, and browser services. The user explicitly permits Google Docs and browser work. Keep Word as the default deliverable; if the local renderer is unavailable, use a browser or Google Docs export for layout checking without opening desktop Word.

Create and deliver an editable `.docx` file by default. Include the project/title information, personalized business cover letter, table of contents when useful, and the full substantive proposal. The cover letter belongs in the same Word document before the contents and body. Use the letter in the retained `assets/source-proposal.docx` as the structural and voice reference, or the user's newer designated cover letter if supplied. Update recipient, salutation, solicitation, scope, dates, and signatory details throughout; do not carry old project information, reuse a signature image, or reproduce the old letter as a screenshot.

Use the available `documents` skill and bundled workspace runtime for Word authoring. Read [references/word-workflow.md](references/word-workflow.md) for the packaged portable fallback when those capabilities are unavailable and for browser-only rendering recovery. Create the full document with editable text and tables, render it with the available document renderer, inspect every rendered page, and repair layout problems before delivery. Keep images and captions with their equipment sections, repeat pricing-table headers across pages, and check cover-letter fit and contents/page numbers. Save the final file in the task workspace, normally `output/documents/`, with a descriptive opportunity-specific filename. Do not open or automate desktop Word when a renderer is unavailable, and never claim unperformed visual verification.

Return the Word file with a brief chat explanation and any actual information needed to finalize. Do not provide only a chat draft, outline, blank form, or gallery instructions. Honor an explicit later request for chat-only, PDF, Google Docs, or another format. Keep the `.docx` as the default rather than silently converting it into a Google Doc. Respect mandatory solicitation forms and submission instructions; the narrative and cover letter supplement required forms where applicable.

## Draft the proposal

Follow the blueprint and produce full narrative sections, not just headings or a questionnaire. In the absence of buyer-mandated order, use:

- Project/title information, personalized cover letter, and table of contents with verified pagination.
- **1. Company Overview**, including Core Company Information.
- **2. Technical Approach**, using the four delivery phases plus safety, utilities, and readiness.
- **3. Equipment Specifications**.
- **4. Price Proposal**.
- **5. Past Performance**.
- **6. Required Documentation**, with solicitation-specific subsections.

Use consecutive numbering; the example accidentally skips section 3. Do not add a separate executive summary or schedule by default: the cover letter provides the opening overview and the technical phases explain delivery. Add or reorganize sections when the actual solicitation or user requires it.

Write in the proposer's voice, with clear paragraphs explaining the solution, execution, and operational benefit. Use bullets for concrete provisions and tables for pricing and reference records. Match the sample's level of practical detail without padding, repetitive promises, or unsupported superlatives. Adapt the title information, letter, narrative sections, equipment details, prices, and documentation to the new opportunity. Use actual requirements and evaluation factors to make the draft specific, rather than replacing names in generic prose.

Use the price book to populate matching supported rates rather than leaving all prices TBD. Match the exact equipment type, size/configuration, billing period, and qualifying rental term. Show quantity, unit/billing basis, rate, and extension, and retain the source page and calculation in working notes. Calculate rental, delivery, servicing, and other supported charges according to the book and the buyer's schedule. Do not infer a daily rate, multi-year discount, service rate, escalation, tax treatment, or all-inclusive price where the source does not establish it. If a component or billing basis is missing, mark only that component and affected totals for confirmation; a known subtotal may be labeled separately. Keep pricing assumptions or commercial gaps outside an eventual submitted bid when the solicitation prohibits qualifications or alternate terms.

For per-visit/monthly conversions, user-approved overrides or equipment substitutions, read [references/pricing-decisions.md](references/pricing-decisions.md). Every two weeks is not twice monthly. Establish the billing unit and any fixed monthly rate with the user rather than silently converting it. Keep past project approvals scoped to that project. Describe a nonmatching offered model accurately and flag required buyer clarification; a larger unit or approved price does not prove technical compliance.

## Trailer images when useful

Use the user-designated [trailer image catalog](https://docs.google.com/spreadsheets/d/1tu6szuEWANuI0gtqrsl9g_gQa0Vm256YD7UmsEtouOc/edit?gid=943101906#gid=943101906) as the first source of equipment visuals. When images clarify the offered equipment, its layout or relevant features, or the user requests them, read [references/trailer-images.md](references/trailer-images.md) and select appropriate files from the catalog's linked Drive folders. Keep this conditional: respect submission/page restrictions and skip images that add no useful information. Do not add a new approval or image-selection question for routine use of this source.

Match equipment type and configuration before visual quality. Inspect the actual candidate images, choose clear and useful exterior/interior views, and place a small selection alongside the relevant Equipment Specifications subsection with accurate captions. Label unconfirmed units/configurations as representative; distinguish supplied renderings from documentary photos. Image-library membership is not confirmation of availability, specifications, or compliance. Do not automatically substitute stock or generated trailers, or modify equipment features to make an image appear to meet the SOW.

Insert selected images into the Word document with accurate captions, preserved aspect ratios, and useful placement alongside the matching equipment text. Check their final rendered layout. If the user explicitly requests chat-only output, use supported previews or permitted image embeds, or provide a descriptive source-file link when inline display is unsupported. If suitable images are missing or inaccessible, finish the proposal and briefly note the image gap.

## Review and deliver

Check identity and contact consistency; scope, equipment counts and capacity; dates/duration and service frequency; utility/access responsibilities; pricing math and billing units; source support for claims; required clauses and attachments; sequential headings and matching contents. Ensure references describe real approved projects. Remove the old project's buyer, solicitation, dates, prices, capacities, and contacts from the new draft. Do not sign or claim completion of a certification on the user's behalf.

Keep source links, price-book page references/calculations, and a concise source/access note outside the client-facing proposal, so the user can trace material requirements and rates. Never claim an attachment is enclosed when it has not been supplied or actually included. For the default Word deliverable, follow the Documents skill's structural and visual checks and update contents/page references after layout is stable. Confirm the file contains the cover letter, complete proposal, pricing tables, and selected images before returning it.

Deliver the draft in the requested format, marked as a draft. Separately provide a concise **Information needed to finalize** list containing only actual gaps or decisions. If everything is supplied, omit that list. Creation of a draft does not authorize submitting it, sending it to the buyer, or signing it.
